# Native GPU and frame rendering: deeper static findings

Evidence inspected: `research/cpu-memory-gpu-decomp.txt`, `research/cpu-memory-gpu-followup-decomp.txt`, `research/cpu-memory-gpu-details-decomp.txt`, and `research/runtime-data-decomp.txt`, direct headless Ghidra exports of ARM32 program SHA-256 `182704ecaa5277ca837544272ac81cd704a1d0b8eb215afea04d143396d7affa`; address inventory cross-checked in `research/runtime-symbols.tsv`. This is static decompiler evidence, not a live GPU capture and not REA Evidence. No protected playback internals were studied. All function addresses below are function entry addresses in that binary.

## Confidence and limits

“Observed” means the export shows a call, branch, data structure, literal, or sequence. “Inferred” means that sequence supports an explanation but does not establish its full contract. “Unknown” means a necessary implementation, indirect target, literal value, or runtime measurement is absent.

Several function prototypes are wrong or incomplete. Examples include `beginRendering` treating the apparent queue receiver as an `ApiContext`, `glColorMask` showing only three arguments, `glClearColor` showing only three arguments, `glBindBuffer` sometimes omitting its object argument, and `glDrawArrays` sometimes omitting its count. ARM float register recovery also produces implausible expressions, particularly in `TextureGroup::actualOptimizeTemp`. Therefore omitted parameters are not zeros and displayed inferred types are not reliable object definitions. Empty static caller lists do not mean functions are unused; virtual dispatch is common here.

## Frame preparation, rendering, and finalization are distinct

Observed: `Gfx::IEngine::IEngine` at `0x002e7ba8` creates two drawing contexts, a render queue, and three `ClipRender` objects. The three clip objects go into a deque at receiver offset `+0xac`. A second deque begins at `+0xd4`; another pointer at `+0x108` retains the last selected clip object. Mutexes protect the scene/context, queue exchange, and other work lists. The constructor also starts a platform thread, but this export does not identify its entry point or prove which later frame method runs on which thread.

Observed: `Gfx::IEngine::processFrame` at `0x002e8bc8` decides whether to prepare a scene update using decoded-image availability, newly loaded fonts, the drawing tree's dirty result, and an explicit flag (`param_1 & 2`). When work is needed, it takes a clip object from the first deque, clears it to the output dimensions, builds a group around `IDrawingContext::updateNextGen` (`0x002ebafc`), optionally updates the debug overlay, processes clip history, records counters, calls `ClipRender::done` (`0x003095d0`), and enqueues the result in the second deque. With no update, it enqueues a null pointer. If no reusable clip object is available, it returns rather than showing a wait in this method.

Inferred: these are reusable frame preparation containers with bounded in-flight work. There are three initially allocated containers, but that is not evidence of three EGL swapchain buffers, triple buffered presentation, or three full-screen GPU textures. It is also not yet evidence of a latest-frame-wins discard policy: this method appends, and the rendering method removes from the front.

Observed: `Gfx::IEngine::renderFrame` at `0x002e80b4` removes one queued result under the queue mutex. When the queue is empty, or the queued value is null, it tries the retained `+0x108` object. On a reuse path it calls `ClipRender::updateDynamicContent` (`0x00309614`) unless a force flag is set. That helper resets byte `+0x8e`, calls `DrawImageIntent::updateTexture` (`0x00316862`) for registered intents, and ORs their returned change indicators. The returned value feeds the engine's status calculation (`2` minus that result); a status of `1` reaches `ClipRender::renderFrame`. With boolean zero/one intent results, a changed texture gives status one and an unchanged retained plan gives status two. Full caller-facing status names remain unknown.

Observed: the same render method invokes a queue virtual function at slot `+0` with an API context before its successful rendering branch. In that branch it releases the previous retained object's render resources with `ClipRender::releaseRender` (`0x00309658`), returns that object to the first deque, and retains the selected one. Actual `ClipRender::renderFrame` execution occurs only for status `1`. After that, it processes deferred scratchpad texture loads and calls `ScratchpadCache::endFrame` (`0x00308218`). Thus beginning the queue's rendering scope and doing housekeeping are not equivalent to rebuilding or replaying the scene.

Observed: `Gfx::IEngine::finalizeFrame` at `0x002e7080` can independently build a secondary drawing-context group into a lazily allocated fourth `ClipRender`. It runs history processing and `done`, invokes queue slot `+4` with `0`, and renders that clip with the third boolean argument set true. It always invokes queue slot `+8` at the end. The secondary-context role is inferred to be an additional composition layer; its product meaning is unknown.

Observed: raw data confirms `OpenGlRenderQueue::vtable` at `0x01231140`, with two metadata words before callable address point `0x01231148`. Relative to that callable address point, slots `+0`, `+4`, `+8`, `+0xc`, `+0x10`, `+0x14`, `+0x18`, and `+0x1c` resolve to `beginRendering`, `beginFrame`, `endRendering`, `setRenderTarget`, `clearRenderTarget`, `process`, `drawMeshObject`, and `releaseHandles`. The low bit in stored function pointers indicates Thumb code; function entry addresses in this report omit it. The frame methods' queue-call identities are therefore confirmed, rather than merely signature-based matches.

**Render versus present:** none of these exported frame methods shows an EGL swap/present call, swap interval selection, a platform compositor submission, or a presentation timestamp. In particular, `OpenGlRenderQueue::endRendering` restores framebuffer/renderbuffer bindings and deletes temporary handles; that behavior is not presentation. A retained clip object can avoid rebuilding scene commands while still drawing a target again. This evidence does not prove that an unchanged UI retains the screen framebuffer, skips every GL draw, or skips display refresh.

## ClipRender retains processed work and manages temporary targets

Observed: `Gfx::ClipRender::renderFrame` at `0x0030acc8` distinguishes a first/processed path through byte `+0x8c`, and a further-change path through byte `+0x8e`. If already processed and no further change is marked, it jumps directly to `drawTarget(0, ...)`. With the additional-change marker set, it resets relevant counters, clears registered image intents, restores the polygon pool to a saved state, releases extra temporary scratchpads, and processes the group again. On its initial path it loads referenced scratchpad textures, creates a root temporary record carrying the supplied target scratchpad, and saves a polygon-pool restore state.

Observed: `Gfx::ClipRender::drawTarget` at `0x0030a3e0` walks temporary records whose dependency field refers to the requested target, marks each visited, and recursively draws dependencies before the requested target. A non-null scratchpad whose flag byte `+0x3c` already contains bit one returns without drawing that target. Otherwise it clears the render queue's operation list to the target's dimensions, prepares an orthographic camera and a translation from target bounds, asks the group's virtual draw method to populate operations, selects the target, and processes them. Only if both group generation and queue processing report success does it set the scratchpad valid-content bit. It then calls `clearRenderTarget`. A separate early exit handles a particular non-root group type value eight with dependency zero; the semantic group label is unresolved.

Inferred: prepared operations and valid offscreen pixels both can be reused. The cached-target early return is direct evidence of avoiding an intermediate redraw. The root/default framebuffer path has no scratchpad validity check of its own and still runs queue processing when this method reaches it; skipping a whole root replay is controlled by the engine's prior unchanged-content decision. Reuse of an offscreen texture and reuse of the whole presented frame remain distinct.

Observed: after `Group::process` (`0x00311364`) and a further group virtual call, `ClipRender::renderFrame` computes ranks using temporary-record dependency/index fields and `calculateTempRank` (`0x0030a114`). Later it draws target index zero. The method also has paths that load textures for image intents, add debug overlays for temporary records, and count unique temporary costs using hashes and `Scratchpad::calculateMemorySize` (`0x004ad820`).

Observed: `ClipRender::releaseRender` (`0x00309658`) releases temporary scratchpads back through the cache and zeros their pointers, releases externally referenced scratchpads, resets and clears image intents, and releases image proxies. It does not simply preserve all GPU references when the container returns to the preparation pool. Any cache-level retention after release is owned by the scratchpad cache; retained preparation containers and retained GPU pixels have different lifetimes.

Inferred: the renderer has a dependency plan for intermediate surfaces. This does not establish whether those intermediates implement opacity groups, filters, masks, blur, or another particular visual effect. Those claims require the relevant group/shader implementations.

Observed: `Gfx::ClipRender::uploadScratchpad` at `0x00309128` is a failure-reporting clone: it constructs diagnostic text and returns zero. The real loading work visible to callers is `ScratchpadCache::loadTexture` (`0x003077e0`). The helper's name must not be treated as proof that this clone uploads pixels.

Observed: `Gfx::ClipRender::updateMemoryUsage` at `0x00308d8c` adds a scratchpad's reported memory size to its accounting and compares that total with the engine's `+0x34` budget. Exceeding the budget produces a trace; the total is still stored. This function alone is accounting/diagnostics, not an admission limit or eviction policy.

Observed: `Gfx::ClipRender::processClipHistory` at `0x0030cda0` sorts a vector of history objects using their integer field at `+4`, then invokes a virtual function for entries whose implementation differs from a recognized default. The export does not identify that ordering field as depth, time, age, z-index, or dirty-region priority. It is not evidence for damage rectangles or hardware scissor optimization by itself.

## TextureGroup can avoid a separate temporary

Observed: `Gfx::TextureGroup::actualOptimizeTemp` at `0x00312768` caches its decision with flag bits in `+0x68`. It obtains group bounds, performs floor/ceil and rectangle intersection operations, and can mark a decision successful without taking the fallback `makeTemp` path. Another path examines a single candidate draw operation, calls `PolyDrawOp::isTempRedundant` (`0x0030e584`), and reuses a value obtained from that operation's shader. Some related flags depend on shader type IDs and the operation's blend-mode field.

Inferred: bounds and an existing drawable/texture can sometimes make an intermediate surface unnecessary. The corrupted float register reconstruction prevents a faithful formula for the bounds calculation; do not turn the displayed `IEngine::instance()` result cast to float into a claimed scale or coordinate transform. The exact optimization predicates need disassembly/register repair or smaller helper exports.

Observed: `Gfx::TextureGroup::makeTemps` at `0x00312934` calls the optimizer first. On failure, it obtains a group blend mode, hashes drawing operations with `DrawOps::getHash` (`0x0030d75c`), mixes additional fields into the hash, and calls `ClipRender::makeTemp` at `0x0030ab00` with group bounds and that hash. It stores the returned temporary and its scratchpad field.

Observed: both bounded `ClipRender::makeTemp` overloads (`0x0030ab00`, `0x0030a9f0`) intersect bounds with the clip extent, reject dimensions below one, then delegate to `makeTempUnbounded` (`0x0030a7e4`). The latter allocates a small temporary record from the polygon pool, appends it to the frame's vector, copies bounds and the content hash, mixes dimensions into that hash, and passes the key and integer dimensions to `ScratchpadCache::acquireScratchpad` (`0x003089d8`). It records the returned scratchpad and group pointer. This connects content/state/dimensions to cache acquisition, while `drawTarget` proves that acquired valid content can skip redraw. Cache collision checks, eviction rules, and lifetime across different clip containers are separate cache questions.

Observed: `PolyDrawOp::isTempRedundant` (`0x0030e584`) restricts reuse to a numeric shader-type mask, constant vertex color with four components equal to one, a four-point polygon matching the rectangular extent, and additional mapping constraints. This is a narrow geometry/color/mapping optimization, not permission to remove arbitrary composition groups. Some mapping field names and the float-sensitive outer bounds calculation remain unresolved. The displayed argument names/types for `makeTemps` are inconsistent with the actual receiver use and should not be copied into an API design.

## OpenGL setup and target lifetime

Observed: `Gfx::OpenGlRenderQueue::beginRendering` at `0x004ac6dc` creates a framebuffer and renderbuffer if handles are absent, checks for zero handles, and obtains existing framebuffer/renderbuffer bindings using `glGetIntegerv` with `0x8ca6`/`0x8ca7`. It records the generated handles in globals as well. `endRendering` at `0x004ac5b4` restores the saved bindings, deletes the generated framebuffer/renderbuffer, and zeros the queue fields.

Observed: `OpenGlRenderQueue::setRenderTarget` (`0x004ac640`) preprocesses operations first. A null target restores the saved framebuffer/renderbuffer; a scratchpad target goes through `ScratchpadCache::setRenderTarget` (`0x00307e34`) and receives a color/depth clear (`0x4100`). It sets the viewport to the current queue dimensions on either successful path. Null here means the framebuffer supplied by the host's prior binding, not necessarily GL framebuffer zero or the physical display.

Observed: `OpenGlScratchpad::initRenderTarget` (`0x004ad3f4`) lazily allocates a 2D texture at the scratchpad's width/height with RGBA internal/data format (`0x1908`), unsigned-byte type (`0x1401`), null initial pixels, linear min/mag filtering (`0x2601`), and clamp-to-edge wrap (`0x812f`). It records successful allocation with flag bit four, and cleans up texture handles on reported GL errors. `OpenGlScratchpad::setRenderTarget` (`0x004ad50c`) requires scratchpad type zero, binds the shared generated framebuffer, attaches its texture at color attachment zero, and optionally allocates a depth-component16 renderbuffer (`0x81a5`) at matching dimensions and attaches it as depth. It drains GL errors. No framebuffer completeness query or multisample resolve appears in these helpers. Actual hardware storage size, color space, driver tiling, and final display surface remain unknown.

Observed: `beginFrame` at `0x004ac538` optionally calls `glClear` with mask `0x4100`, sets color/depth write masks, enables capability `0x0b71`, selects depth comparison `0x0201`, disables `0x0b90` and `0x0c11`, and sets pixel pack/unpack alignment (`0x0d05`, `0x0cf5`) to four. These literals correspond to color/depth clear, depth test/LESS, stencil/scissor disable, and pixel alignment in the GL API. The omitted alpha/fourth-channel arguments mean exact clear alpha and alpha write-mask values are unknown here.

## State sorting and batching

Observed: `Gfx::RenderQueue::preprocess` at `0x0031652c` sorts polygon draw operation pointers using `PolyDrawOp::operator<` (`0x0030e130`). Its exported caller is `OpenGlRenderQueue::setRenderTarget` (`0x004ac640`). It also determines a flag at `+0x14` using operation blend-mode values, ordering fields, and the camera/group pointer at operation `+0x19c`.

Observed: `Gfx::OpenGlRenderQueue::process` at `0x004acbe0` returns immediately for an empty operation vector. It enables polygon attributes, initializes its current vertex count, compares each operation with the preceding state using `PolyDrawOp::compareState` (`0x0030e0f0`), and flushes accumulated vertices through `glDrawArrays` when the state comparison fails and there is accumulated work. It then applies the new state and appends ordinary polygon geometry through `PolyDrawOp::commitToVertexBuffer` (`0x0030e194`). It flushes remaining accumulated work at the end.

Observed: `PolyDrawOp::compareState` (`0x0030e0f0`) requires equal blend mode, `Shader::equal` (`0x002fd95c`), and no camera/group pointer on either operation. Therefore ordinary adjacent polygon operations can batch under a blend-and-shader equality rule; camera mesh groups force a boundary. The call's visible primitive mode is `4` (triangles). Shader equality's own fields are not exported, so texture-only compatibility is not established. Exact runtime draw counts remain unknown, and the decompiler omits the vertex count argument from the flush calls.

Observed: `PolyDrawOp::operator<` (`0x0030e130`) places modes one/three before the other blend modes. Within that class it orders field `+0x194` descending; within the other class it orders that field ascending. Equal values are ordered by shader-type ID. Since modes one/three disable blending in `setState`, this supports separate ordering policies for nonblended and blended work, but the semantic coordinate stored at `+0x194` has not been established. It is not arbitrary global texture sorting, and these exports alone do not prove visual ordering correctness for every scene.

Observed: `setState` at `0x004ac954` changes blend configuration only when the numeric mode differs from the prior operation. Modes zero through five map to concrete GL enable/disable/equation/factor calls: modes one and three disable capability `0x0be2`; zero uses equation `0x8006` with factors `1, 0x0303`; two uses the same equation with factors `0, 0x0303`; four uses separate factors `1,1,1,0x0303`; five also selects separate equations `0x800b,0x8006`. For ordinary polygon operations, it enables the shader after this state handling.

These calls establish blending behavior, but the exported names do not identify the application's enum labels. Calling every texture premultiplied, assigning UI effect names to modes, or assuming a complete blend-mode vocabulary would go beyond the evidence.

Observed: `enable` at `0x004ac890` selects a shader program through `ShaderCompiler::enableProgram` (`0x004adc80`), sets two matrix uniforms indexed zero and one, then invokes the concrete program's apply method. One matrix is produced from a transform multiplication; the other is copied from a shader-owned pointer. The exact projection/model/texture roles of those matrices are unknown without shader declarations/source and uniform lookup code.

Observed: `preDraw` at `0x004ac814` enables attributes zero through three and installs an interleaved 36-byte vertex layout: attribute zero is three floats at the first field, attribute one is three floats at byte 24, attribute two is four normalized unsigned bytes at byte 12, and attribute three is two floats at byte 16. This proves formats and offsets, not each attribute's semantic shader name. `commitToVertexBuffer` (`0x0030e194`) triangulates the polygon into the remaining space of a 65,536-entry buffer, maps each generated point with `VertexMap::mapPoint` (`0x003188b8`), fills an additional per-vertex value, and advances the count. It asserts if triangulation returns as many or more entries than the remaining capacity. `VertexBuffer::advanceHead` (`0x003182c0`) also aborts for a resulting count above 65,535. Thus the buffer reserves 65,536 slots but this path requires a strictly lower final count; exhaustion is an assertion failure, not a demonstrated automatic flush. Flushes visible in `process` occur on state transitions and at the end.

## Mesh and texture-specific work

Observed: `OpenGlRenderQueue::process` at `0x004acbe0` handles operations with a non-null `+0x19c` camera/group pointer through a separate path: it sorts meshes, adjusts `glDepthRangef`, obtains a transformed viewport, draws meshes, restores depth range and full viewport, disables culling when required, and reinstalls polygon attributes. A flag at group `+0xf8` splits the viewport width into two horizontal regions and draws twice. A stereo purpose is plausible but unproved by this export.

Observed: `Gfx::OpenGlRenderQueue::drawMeshObject` at `0x004aca0c` enables a shader, obtains an array buffer through `ScratchpadCache::bindBuffer` (`0x0030756c`), changes culling/front-face state when its cached numeric cull mode changes, installs a 32-byte layout for attributes zero/one/three, calls `glDrawArrays(4, 0, mesh field +4)`, then unbinds the array buffer. Modes zero/one enable culling with `0x0900`/`0x0901` winding; mode two disables it. There is no indexed draw in this function.

Observed: `Gfx::OpenGlArrayBuffer::create` at `0x004ac3c0` lazily creates a buffer only if its handle is zero, binds target `0x8892`, and calls `glBufferData` with size equal to two stored fields multiplied, a CPU data pointer, and usage `0x88e4`. It drains `glGetError`; an error deletes and zeros the new handle. `bind` at `0x004ac44c` refuses a zero handle, binds an existing handle, and also drains errors. These are array-buffer/static-draw literals. They support reusable mesh uploads; they do not establish that all dynamic UI polygons use this buffer or that `STATIC_DRAW` guarantees device-local residence.

Observed: `Gfx::OpenGlTextureProgram::apply` at `0x004afdf4` validates the texture shader, obtains its scratchpad, and calls `OpenGlScratchpad::bindTexture` (`0x004ad944`) with `0x84c0`. For shader IDs four and five, it supplies `Scratchpad::yuvConversionMatrix` (`0x00305908`) and `yuvConversionOffsets` (`0x00305924`) to matrix/three-component uniforms. ID seven supplies another matrix and vector from shader fields. This directly supports YUV conversion parameter handling for two shader variants; the method alone does not identify plane formats, HDR transfer behavior, video decoder sharing, or the purpose of variant seven. The scratchpad helpers provide the format details below.

Observed: `OpenGlScratchpad::bindTexture` (`0x004ad944`) binds the first texture at the requested active texture unit and, when a second handle is present, binds it at the next unit. Scratchpad type four uses target `0x8d65` (external OES); other types use 2D. This proves an external-texture binding path, not how a decoder supplies or synchronizes that texture. `loadTexture` (`0x004ad2a0`) lazily allocates one ordinary 2D handle, and a second for type three, with linear filtering and clamp-to-edge, then delegates pixel upload. `upload` (`0x004ad0ec`) uses RGBA unsigned bytes for types zero/one, alpha unsigned bytes for type two, and two textures for type three: a rounded-even full-size alpha plane followed by a half-size luminance-alpha plane at a calculated source offset. This is consistent with a two-plane 4:2:0 representation, but channel/chroma order and exact YUV standard are not established here. The method calls `glTexImage2D`; no subimage update appears in this helper.

Observed: `ShaderCompiler::enableProgram` (`0x004adc80`) indexes a program cache by shader-type ID and lazily constructs missing entries through `makeProgram` (`0x004adb34`), then calls `glUseProgram`. The switch covers 64 IDs and names concrete texture, texture/color blending, video texture, blur, color, glass, glossy, HSL, Phong, mask, circular rounding, shadow, debug overlay, and texture/texture blending program classes. These class names demonstrate supported program families, not which effects a particular screen executes or their shader math. Actual compile/link code, uniform names, and shader source remain outside this export.

## Synchronization, scheduling, and unsupported performance claims

Observed: the frame exchange uses platform mutexes. `IEngine::renderFrame` also performs `SaveDc::download` (`0x002e9cbc`) for a prior list and later `SaveDc::render` (`0x002e99c0`) for incoming work; it posts a semaphore after transferring downloaded items to another protected list. Actual readback implementation and its GL stall behavior are not exported here.

Observed: `Gfx::IEngine::suspend` at `0x002e7384` suspends the image server and, on its recognized default path, records the current thread identity, invokes queue virtual slot `+0x1c`, and calls `ScratchpadCache::releaseHandles` (`0x00306568`). A different virtual implementation is delegated to otherwise. Raw vtable data confirms that slot as `OpenGlRenderQueue::releaseHandles` (`0x004ac5a8`), which calls `ShaderCompiler::releaseHandles` (`0x004adcac`). The compiler unbinds its program and 2D textures on units zero through two when releasing populated entries, invokes each program's cleanup virtual function, and clears its 64 cache slots. Combined with lazy program creation, this supports recreation on later use; exact GL context recreation and full platform resume sequencing remain unknown.

Observed: `Gfx::RenderQueue::drainPipeline` (`0x004ac810`) calls the indirect import `PTR_glFinish_012683bc`. The original export identifies its callers as `ScratchpadCache::ensureMaxSurfaceMemoryUsage` (`0x00307774`), `loadTexture` (`0x003077e0`), `initRenderTarget` (`0x00307b70`), and `setRenderTarget` (`0x00307e34`). `ensureMaxSurfaceMemoryUsage` first tries to free unused memory while over budget; after it cannot make further progress, it drains, advances its reuse/age counter, and tries again. The upload/target paths likewise drain on a retry/failure path, not unconditionally on every frame. These are concrete GPU completion waits under cache/allocation pressure; frequency and duration require measurement.

The `DataMemoryBarrier` operations in `ClipRender::renderFrame` are CPU memory-ordering instructions and are separate from that GL completion wait. No fence-object or explicit `glFlush` implementation appears in the focused exports. Buffer allocation, texture upload, readback, driver submission, target rebinding, and external presentation may introduce additional stalls. Nothing here quantifies GPU execution time, presentation latency, vsync, energy use, or sustained frame rate. CPU tick counters around frame calls cannot by themselves be relabeled GPU timings.

## Lessons for Bloob

These are design ideas to evaluate in Bloob's native implementation. Their direct applicability depends on what its selected graphics backend exposes; they do not require reproducing the reference's private APIs.

- Keep scene preparation, command replay, resource housekeeping, and presentation separate in diagnostics. An idle drawing tree can save CPU preparation while a platform continues refreshing the display. Measure each layer before attributing smoothness or idle cost to one of them.
- Retain prepared scene work and update it for real inputs: tree changes, completed image decoding, fonts, and dynamic content. Give retained plans explicit validity and invalidation rules. The reference's separate dirty and dynamic-content paths make this distinction concrete (`0x002e8bc8`, `0x002e80b4`, `0x0030acc8`).
- Reuse a bounded pool of preparation objects and exchange ownership briefly under synchronization. Do not infer or reproduce a swapchain policy from the three initial clip objects (`0x002e7ba8`).
- Prefer intermediate surfaces only where composition needs them. Content/state hashes and redundant-temporary checks suggest ways to avoid repeating offscreen work, but budget enforcement and reuse rules must be designed explicitly (`0x00312768`, `0x00312934`, `0x00308d8c`).
- Batch compatible adjacent draw work and cache actual render state. Preserve ordering where transparency/composition requires it; first inspect the comparator rather than assuming sorting is universally safe (`0x0031652c`, `0x004acbe0`, `0x004ac954`).
- Use explicit suspend/resume resource ownership, and track texture/buffer/upload/readback costs separately. An accounting threshold that merely logs excess use should not be mistaken for a reliable memory cap (`0x002e7384`, `0x00308d8c`).
- Track resource pressure alongside frame latency. The reference's cache can deliberately wait for prior GPU work with `glFinish` before retrying reclamation/allocation; a cache miss or budget shortage can therefore become a visible frame stall (`0x004ac810`, `0x00307774`). Avoid interpreting low scene-preparation time as proof that a frame cannot stall later.

## Remaining unknowns

The helper exports resolve the original target, batch-key, capacity, texture-format, program-cache, and queue-vtable questions. These are the material limits that remain:

- **Presentation:** the platform caller and final display/compositor submission are outside this GPU report. These methods restore the host target and finish their own rendering scope; they do not show vsync policy, swap interval, presentation timestamps, or a frame's display latency.
- **Measured performance:** no GPU capture or timing query establishes draw counts per screen, cache hit rates, intermediate redraw frequency, allocation pressure, `glFinish` frequency/duration, or upload/readback stalls. Static support for reuse is not a measured speedup.
- **Ordering and shader semantics:** `Shader::equal` at `0x002fd95c`, producers of ordering field `+0x194`, shader constructors/source, and uniform definitions are needed to name every state field, prove comparator ordering for a given scene, or describe exact visual math. The exported class families do not prove active use by a particular UI screen.
- **Cache lifetime:** `acquireScratchpad` at `0x003089d8` and the broader cache study establish cross-frame matching, eviction, safe reuse ages, and retained memory. This GPU report establishes the keyed request and the valid-content draw skip; it does not assign collision semantics or guarantee indefinite retention.
- **Resource transfer:** `OpenGlScratchpad::download` at `0x004acf58` and `SaveDc::download` at `0x002e9cbc` still need their implementations to quantify readback or synchronous transfer. An external OES binding path does not establish decoder ownership, zero-copy operation, or its synchronization contract.
- **Float-sensitive optimization:** exact outer bounds calculations in `TextureGroup::actualOptimizeTemp` at `0x00312768` require register/literal repair before stating their formula. The narrow redundant-rectangle predicate and bounded temporary intersection are independently visible and do not repair that decompiler result.
- **Target cleanup and platform lifecycle:** `clearRenderTarget` at `0x004ac5f4` is identified by the vtable and called after processing, but its body is not in these focused helper exports. Full platform context loss/resume, output color space, framebuffer completeness beyond GL error checks, and display-surface ownership are not established.
